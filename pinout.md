# Heltec WiFi Kit 32 V2 - Dog Door Pinout

This project uses the original ESP32-based **WiFi Kit 32 V2**, not the
ESP32-S3-based V3 and not the WiFi LoRa 32. GPIO numbers below are ESP32 GPIO
numbers, not physical header positions. Confirm the PCB revision before wiring.

## Project Wiring

| Signal | GPIO | Configuration | Meaning |
| --- | --- | --- | --- |
| Inside PIR | 17 | Digital input | HIGH = motion |
| Outside PIR | 2 | Digital input | HIGH = motion |
| Open reed switch | 13 | Input with internal pull-up | LOW = fully open; switch connects to GND |
| Closed reed switch | 12 | Input with internal pull-up | LOW = fully closed; switch connects to GND |
| Motor M1 | 25 | Digital output, no PWM | Opening: HIGH; stopped: LOW |
| Motor M2 | 26 | Digital output, no PWM | Closing: HIGH; stopped: LOW |
| OLED SDA | 4 | I2C data | SSD1306 address 0x3C |
| OLED SCL | 15 | I2C clock | Shared onboard display bus |
| OLED reset | 16 | Output | Active LOW |
| Vext enable | 21 | Output | Firmware drives LOW to enable external power |

The OLED/Vext assignments above record the current firmware wiring. Use the
manufacturer's revision-specific schematic to confirm onboard connections;
do not assume GPIO 21 is a universal Vext enable on every Heltec board.

## ESP32 Electrical Constraints

- GPIO uses **3.3 V logic**; do not apply 5 V to GPIO inputs.
- All sensors, controller, and motor driver need a common ground.
- GPIO 34-39 are input-only and have no internal pull-ups/pull-downs.
- GPIO 6-11 are used by flash; do not repurpose them.
- GPIO 0, 2, 5, 12, and 15 are boot-strapping pins. External wiring can prevent
  boot or flashing. This project uses GPIO 2, 12, and 15.
- In particular, GPIO 12 HIGH during reset can select a 1.8 V flash supply on
  the original ESP32. Verify boot reliability when the closed reed is open;
  avoid adding an external pull-up to GPIO 12.
- GPIO 1/3 normally serve the USB serial UART; GPIO 0 is normally associated
  with the BOOT button. Consult the diagram for actual header positions.
- ADC2 analog measurements conflict with Wi-Fi on the original ESP32. This
  does not prevent the digital reads used by this project.
- Motor power must go through the driver, never a GPIO or the board's 3.3 V rail.
  The listed motor stall current (1.2-2.0 A) exceeds the listed L9110S driver
  rating (800 mA); verify driver suitability and thermal protection.

## Network Diagnostics

- Static address: `192.168.1.251`; gateway/DNS: `192.168.1.1`; mask: `255.255.255.0`.
- Reserve/exclude this address in the router's DHCP pool to avoid conflicts.
- Live page: <http://192.168.1.251:5000/>.
- JSON values: <http://192.168.1.251:5000/api/pins>.
- Events: <http://192.168.1.251:5000/api/events>. The dashboard shows the last
  reset reason and the latest 24 events, newest first, with uptime timestamps.
  Events include state transitions, debug commands, safety stops, Wi-Fi changes,
  and OTA activity. Event history is RAM-only and clears on reboot; the new boot
  reports the ESP32 reset reason. A severe power loss can report power-on rather
  than brownout, so the reset reason alone cannot rule out a supply problem.
- The page reports the six application GPIOs, including digital motor-pin
  readbacks, not measured voltages; OLED bus pins are not probed.
- The web page and motor debug commands have no password requirement. Anyone
  who can reach the server can control the motor; use a trusted LAN and do not
  expose this server or OTA to the Internet. OTA authentication is unchanged.
- Wi-Fi and OTA credentials live in Git-ignored `src/ota_config.h`.
- OTA is the default PlatformIO environment. Select **General > Upload** under
  `heltec_v2_ota` (or Default), or run `pio run --target upload`.
- `ota_upload.py` reads `OTA_PASSWORD` directly from the local credential header
  and fixes the upload address to `192.168.1.251`, including when the IDE has a
  stale COM3 selection. No password environment variable is required. Avoid
  verbose uploads/environment dumps when sharing logs: flags can contain secrets.
- **Upload and Monitor** adds a USB serial monitor; it is not wireless monitoring.
  With USB disconnected, use Upload and the web dashboard for diagnostics.
- `heltec_v2` remains available for explicit USB recovery uploads.
- VS Code **Terminal > Run Task > DogDoor: OTA Upload** uses the explicit task
  in `.vscode/tasks.json`. PlatformIO's sidebar Project Tasks are generated by
  the extension from the environments in `platformio.ini`; they are not stored
  in that JSON file. The corrected upload hook also supports those generated tasks.

## Motor Debug

- Enable Debug mode in the dashboard; no password is needed. Automatic
  motion sensing and serial movement commands are suspended while debugging.
- Open/Close latch the selected output without a time cutoff. The slider selects
  0 (LOW/off) or 1 (HIGH/full drive), defaulting to 0. Other values are rejected.
- Closing the browser does not stop the output. Use Stop before leaving the
  controller unattended; avoid stalling the motor or overheating the driver.
- Both automatic and debug movement now use full drive rather than PWM. The
  documented motor stall current exceeds the driver rating: disconnect motor
  power for logic tests and use a suitably rated driver before loaded testing.
- Stop immediately zeros both outputs and leaves Debug mode enabled, even if
  automatic operation was previously active.
- A separate software timer checks every 10 ms and stops a debug output at its
  target limit, on Wi-Fi disconnect, or on OTA lockout. There is no debug timeout.
  Software timing is not a replacement for electrical current limiting or a
  hardware emergency stop. Replacing the undersized driver remains recommended.
- Stop the current output before requesting another direction. Both
  outputs cannot be driven together through the debug API.
- Disabling Debug mode stops the motor and resumes automatic operation at a
  known limit; if between limits, the controller enters Fault rather than seeking.
- Debug mode defaults to enabled in the firmware. Startup keeps both outputs
  LOW and never seeks a limit while debugging. UI mode changes are not persisted
  across reboot; reboot restores the compiled default.
- External pull-downs on both driver inputs keep them LOW while the ESP32 is
  resetting or disconnected; software cannot control GPIO during reset.
- For an L9110S, equal input levels normally produce equal motor-terminal levels
  (no drive/braking), not simultaneous forward and reverse motion. Independent
  PWM signals on both inputs can create alternating drive and current spikes.
  Confirm the truth table for the exact driver fitted before experimenting.
